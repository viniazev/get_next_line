================================================================================
GET_NEXT_LINE - IMPROVEMENT RECOMMENDATIONS
================================================================================

After analyzing the code, here are key inefficiencies and recommended improvements:

================================================================================
1. CURRENT INEFFICIENCIES
================================================================================

A) EXCESSIVE MEMORY REALLOCATIONS
   Current Issue:
   - Every ft_strjoin call allocates NEW memory
   - With BUFFER_SIZE=1, a 1KB line requires 1000+ malloc/free cycles
   - Each reallocation copies all previous data
   
   Example with BUFFER_SIZE=1 and "Hello\n":
   - Iteration 1: malloc(2) -> "H\0"
   - Iteration 2: malloc(3) -> "He\0" (old "H" freed)
   - Iteration 3: malloc(4) -> "Hel\0" (old "He" freed)
   - Iteration 4: malloc(5) -> "Hell\0" (old "Hel" freed)
   - Iteration 5: malloc(6) -> "Hello\0" (old "Hell" freed)
   - Iteration 6: malloc(7) -> "Hello\n\0" (old "Hello" freed)
   
   Result: 6 allocations + 5 deallocations for one simple line!

B) REDUNDANT NEWLINE SEARCHING
   Current Issue:
   - Newline searched in read_store() using ft_strchr()
   - Searched again in extract_line() to find split point
   - Searched again in ft_separate() to find split point
   - Total: 3+ passes through same data looking for '\n'

C) CHARACTER-BY-CHARACTER COPYING
   Current Issue:
   - extract_line() uses while loop to copy (chars individually)
   - ft_separate() uses while loop to copy (chars individually)
   - No use of optimized libc functions like memcpy
   - Compiler may not optimize these loops effectively

D) INEFFICIENT ft_strlen USAGE
   Current Issue:
   - ft_strjoin calls ft_strlen twice (s1 and s2 separately)
   - Could cache length or use single pass
   - No length validation before operations

E) NO PREALLOCATED BUFFER
   Current Issue:
   - Could allocate a larger temporary buffer once
   - Reuse it instead of malloc/free every read cycle
   - Reduces allocator overhead

================================================================================
2. RECOMMENDED IMPROVEMENTS
================================================================================

IMPROVEMENT #1: LARGER INITIAL BUFFER & REUSE
================================================================================
Current approach: malloc/free tiny buffer every read
Better approach: Allocate larger buffer once, reuse it

PSEUDO-CODE:
```
char *read_store(int fd, char *stash, char *buff, size_t buff_size)
{
    int readstatus;
    
    // buff is now REUSED, not allocated/freed each time
    // buff already allocated outside this function
    
    while (!ft_strchr(stash, '\n'))
    {
        readstatus = read(fd, buff, buff_size);
        if (readstatus <= 0)
            break;
        buff[readstatus] = '\0';
        stash = ft_strjoin(stash, buff);
    }
    return (stash);
}

// In get_next_line:
char buff[BUFFER_SIZE + 1];  // Stack allocation, no malloc needed
stash = read_store(fd, stash, buff, BUFFER_SIZE);
```

IMPROVEMENT #2: SINGLE-PASS NEWLINE HANDLING
================================================================================
Current: Searches for newline 3+ times
Better: Search once, cache position, reuse for all functions

PSEUDO-CODE:
```
int find_newline(const char *str)
{
    int i = 0;
    while (str[i] && str[i] != '\n')
        i++;
    if (str[i] == '\n')
        i++;  // Include the newline
    return i;
}

// Then use this value in multiple places:
int line_end = find_newline(stash);
char *line = extract_line_at(stash, line_end);
char *remaining = get_remainder_at(stash, line_end);
```

IMPROVEMENT #3: USE MEMCPY INSTEAD OF LOOPS
================================================================================
Current: Manual character copying
Better: Use optimized memcpy

BEFORE:
```
while (s1[++i])
    catstr[i] = s1[i];
while (s2[++j])
    catstr[i + j] = s2[j];
```

AFTER:
```
memcpy(catstr, s1, len_s1);
memcpy(catstr + len_s1, s2, len_s2);
```

IMPROVEMENT #4: PREALLOCATE STASH WITH GROWTH STRATEGY
================================================================================
Current: Exact-size allocation each time
Better: Allocate more than needed (power of 2), reduce reallocs

EXAMPLE:
Instead of malloc(100), allocate malloc(128) 
Next time, if need 200, allocate malloc(256)
This reduces allocation count from O(n) to O(log n)

PSEUDO-CODE:
```
size_t get_next_power_of_2(size_t current_size)
{
    size_t power = 1;
    while (power < current_size)
        power *= 2;
    return power;
}

// Calculate new size with growth
new_capacity = get_next_power_of_2(strlen(stash) + strlen(buff) + 1);
```

IMPROVEMENT #5: COMBINE FUNCTIONS FOR EFFICIENCY
================================================================================
Current: Three separate functions doing similar operations
Better: Single function that extracts line AND remainder in one pass

PSEUDO-CODE:
```
typedef struct {
    char *line;
    char *remainder;
} t_line_result;

t_line_result extract_and_separate(char *stash)
{
    t_line_result result = {NULL, NULL};
    int i = 0;
    
    // Find newline position (single pass)
    while (stash[i] && stash[i] != '\n')
        i++;
    
    if (stash[i] == '\n')
        i++;
    
    // Allocate line
    result.line = malloc(i + 1);
    if (!result.line)
        return result;
    
    // Copy line (one memcpy)
    memcpy(result.line, stash, i);
    result.line[i] = '\0';
    
    // Handle remainder (if exists)
    if (stash[i])
    {
        result.remainder = malloc(strlen(stash + i) + 1);
        if (result.remainder)
            strcpy(result.remainder, stash + i);
    }
    
    free(stash);
    return result;
}
```

IMPROVEMENT #6: BETTER ERROR HANDLING PATTERN
================================================================================
Current: Scattered error checks
Better: Centralized error cleanup

BEFORE:
```
if (!buff)
    return (free(stash), NULL);
// ... later ...
if (readstatus == -1)
    return (free(buff), free(stash), stash = NULL, NULL);
```

AFTER:
```
char *cleanup_and_return(char *buff, char *stash, int error)
{
    if (buff)
        free(buff);
    if (error)
    {
        if (stash)
            free(stash);
        return NULL;
    }
    return stash;
}
```

3. COMPLETE OPTIMIZED ALGORITHM
================================================================================

Here's a high-level redesign that combines all improvements:

```
OPTIMIZED APPROACH:

1. Preallocate large stash buffer (e.g., 4KB) instead of growing from 0
   - Reduces allocation count significantly
   - Use on stack if possible (BUFFER_SIZE allows)

2. Use single ft_strchr pass to locate '\n'
   - Cache position
   - Reuse for line extraction and separation

3. Use memcpy for all data copying
   - Faster than manual loops
   - Better compiler optimization

4. Combine extract_line and ft_separate logic
   - Single malloc for line
   - Single malloc for remainder (if needed)
   - Eliminates redundant passes

5. Smart buffer management
   - Stack buffer for reading (BUFFER_SIZE)
   - Heap buffer for stash with power-of-2 growth
   - Reduce allocation/deallocation overhead

FLOW:
get_next_line(fd)
  │
  ├─→ is stash empty?
  │    └─ if yes: read from file
  │       └ allocate BUFFER_SIZE stack buffer
  │       └ read into buffer
  │       └ append to stash using ft_strjoin_optimized
  │
  ├─→ find newline position (single pass)
  │
  ├─→ extract_and_separate (combined operation)
  │    ├─ allocate line
  │    ├─ memcpy line data
  │    ├─ allocate remainder (if exists)
  │    ├─ memcpy remainder data
  │    └─ free old stash
  │
  └─→ return line
```

4. PERFORMANCE COMPARISON
================================================================================

Reading a 10KB file with BUFFER_SIZE=1024:

CURRENT IMPLEMENTATION:
- Number of read() calls: ~10
- Number of malloc calls: ~15-20 (for stash reallocations)
- Number of malloc calls: ~10 (for extracted lines)
- Total allocations: ~25-30
- Memory copied: ~10KB of stash + 10KB of lines = 20KB total
- Passes through stash data: 3+ per line

OPTIMIZED IMPLEMENTATION:
- Number of read() calls: ~10 (same)
- Number of malloc calls: ~4 (stash with power-of-2 growth)
- Number of malloc calls: ~10 (for extracted lines, same)
- Total allocations: ~14
- Memory copied: ~10KB of lines only (no stash recopying)
- Passes through stash data: 1 per line

IMPROVEMENT: ~50% fewer allocations, significantly faster string ops

================================================================================
5. MEMORY USAGE COMPARISON
================================================================================

Current: Reading "Hello\nWorld\n" with BUFFER_SIZE=1

Allocations:
1. buff malloc (2 bytes) → free
2. stash malloc (2 bytes) = "H"
3. stash malloc (3 bytes) = "He" (old freed)
4. stash malloc (4 bytes) = "Hel" (old freed)
5. stash malloc (5 bytes) = "Hell" (old freed)
6. stash malloc (6 bytes) = "Hello" (old freed)
7. stash malloc (7 bytes) = "Hello\n" (old freed)
8. line malloc (7 bytes) = "Hello\n"
... and so on

Peak memory: 7 bytes + 7 bytes (stash + line) = 14 bytes
Total operations: 15+ malloc/free pairs for 12 bytes of data

Optimized: Reading same data with pre-allocated buffer

Allocations:
1. stash preallocate (1024 bytes) on stack or heap once
2. buff (1024 bytes) on stack, reused
3. line malloc (7 bytes) = "Hello\n"
4. stash reuse for "World\n"
5. line malloc (7 bytes) = "World\n"

Peak memory: 1024 + 1024 (stash + buff) = 2048 bytes
Total operations: 2-3 malloc pairs for 12 bytes of data

Note: More memory used but 5-10x fewer allocations = faster

   Impact: No malloc/free overhead

4. SIMPLIFY ft_strchr return:
   Current logic has extra check
   Can be streamlined
   Impact: Cleaner code, tiny perf gain

5. REDUCE ft_strlen calls in ft_strjoin:
   Cache lengths passed as parameters
   Impact: Fewer iterations

================================================================================
7. TRADE-OFFS TO CONSIDER
================================================================================

A) Larger BUFFER_SIZE
   PRO: Faster, fewer system calls, fewer allocations
   CON: More memory used per read, wastes memory on small files
   RECOMMENDATION: Use 4096 or match system page size (4096 on most systems)

B) Pre-allocated stash
   PRO: Predictable memory, fewer allocations
   CON: May use more memory than current approach
   RECOMMENDATION: Use power-of-2 growth (double when full)

C) Power-of-2 growth vs exact-size
   PRO: Far fewer allocations
   CON: May waste up to 50% memory
   RECOMMENDATION: Use power-of-2 for interactive/production code

D) Stack vs Heap buffers
   PRO (Stack): Faster, automatic cleanup
   CON (Stack): Limited size, thread issues
   RECOMMENDATION: Use stack for BUFFER_SIZE up to 8KB, heap for larger

E) Combining functions
   PRO: Single pass, fewer redundant operations
   CON: More complex logic
   RECOMMENDATION: Worth it for production, optional for learning

9. MODERN C ALTERNATIVES
================================================================================

Instead of manual malloc/free, consider:

A) getline() - POSIX function
   - Handles all memory management
   - Much simpler: char *line = NULL; getline(&line, &len, file);
   - Portable and well-tested
   - PRO: Simple and efficient
   - CON: May not be available on all systems

B) Read entire file then parse
   - Simpler logic
   - Better performance for small/medium files
   - PRO: Fewer allocations, cache-friendly
   - CON: High memory use for large files

C) mmap() + parsing
   - Memory-mapped file I/O
   - OS handles paging
   - PRO: Extremely fast, automatic page caching
   - CON: Complex, platform-specific
